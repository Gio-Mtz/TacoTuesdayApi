# ADR-0005 — The unique index decides duplicates, and the host picks the provider

- **Status:** accepted
- **Date:** 2026-09-29
- **Supersedes:** the storage half of [ADR-0004](0004-leads-endpoint.md). The contract it
  defined — 201 then 200 with `alreadyRegistered: true`, never 409 — is unchanged.

## Context

ADR-0004 shipped `POST /api/leads` with the waiting list in a `ConcurrentDictionary`, and
wrote down what that cost: **the list does not survive a restart, and each replica keeps its
own.** The Container App runs with `--min-replicas 0`, so an address could be accepted, the
container could scale to zero, and the address would be gone with nobody the wiser — which is
why the landing page has not been sent to a single person yet.

That is the only thing this story is for. Everything below follows from having to answer one
question honestly: *is this address already on the list?* — where "the list" is now a table
that several replicas write to at the same time.

Two constraints from [EQUIPO - Roles y reglas] shape the rest:

- **Nothing here can be compiled or run by Claude.** No .NET SDK, and the Microsoft package
  hosts are blocked. This story ships `[requiere verificación de Gio]`.
- Because of that, the .NET surface per story is kept deliberately small, and anything
  *generated* — a migration, a model snapshot — is generated by the tool, not hand-written.

## Decision 1 — Duplicates are resolved by the unique index, not by a lookup

`EfCoreLeadStore` inserts, and catches the failure:

```csharp
db.Leads.Add(lead);
try { await db.SaveChangesAsync(ct); return new(lead.Id, AlreadyRegistered: false); }
catch (DbUpdateException) { /* find the id that won, return it */ }
```

### Options considered

**A. `SELECT` then `INSERT`.** Look the address up; if it is not there, write it.

- Pros: reads like the sentence it implements. No exception on a normal path.
- Cons: **it is a race, and the race is the entire feature.** Two visitors submitting the same
  address inside the same few milliseconds both find nothing and both insert. It passes every
  test, on every machine, and fails in production once, months later, leaving a duplicate row
  and no explanation. `--min-replicas 0` scaling up to two under a burst is exactly the shape
  of traffic that triggers it.

**B. A transaction with `SERIALIZABLE`, or a `HOLDLOCK` hint.** Correct, and it turns every
signup into a lock on a range of a unique index — paying, on every request, for a collision
that happens on a handful.

**C. Insert and let the index be the judge.** ← chosen.

- One statement. The database, which is the only thing that can see all replicas at once,
  decides. Exactly one `INSERT` can win; the loser gets a `DbUpdateException`, and **only on
  that branch** does a `SELECT` run, to find out which id won.
- The cost is an exception on a path that is not exceptional. That is real, and it is the
  cheaper of the two prices: the alternative is a correctness hole with no symptom.

### Why the exception is not inspected

The tempting next line is `if (sqlException.Number is 2601 or 2627)`. It is not there, because
it would tie this class to SQL Server — and the tests run on SQLite precisely so the index they
violate is a real one. A provider-specific check would mean **the tests exercise a different
branch than production does**, which is worse than no check at all.

Instead: after the failure, look for the address. There → it was a duplicate. Not there → the
insert failed for some other reason (a dropped connection, a table that is not there yet) and
the exception is rethrown untouched. Telling somebody they are on a list they are not on is the
one outcome this must never produce.

## Decision 2 — The module owns the model; the host owns the provider

`LeadsModule` exposes two calls:

- `AddLeadsModule()` — endpoints and handlers.
- `AddLeadsPersistence(Action<DbContextOptionsBuilder>)` — the context, the store, the
  readiness check.

`TacoTuesday.Modules.Leads` references `Microsoft.EntityFrameworkCore` and `.Relational`, and
**no provider**. `Program.cs` passes `UseSqlServer(...)`; the tests pass `UseSqlite(...)`.
`ModuleBoundaryTests.Modules_must_not_depend_on_a_database_provider` is what keeps it that way
after everybody has forgotten this paragraph.

The alternative — `AddLeadsModule(connectionString)` with `UseSqlServer` inside the module —
is one less concept and would have made the SQLite tests impossible, which would have made the
duplicate branch above untested. The seam is not architectural taste; it is what buys the test.

## Decision 3 — No schema, for now

Schema-per-module (`leads.Leads`) is the tidier boundary and it is deliberately not here.
SQLite has no schemas, and the tests run on SQLite so the unique index is real. A mapping that
only works on one provider would cost exactly the test that matters.

While the table is empty, adding the schema later is a rename in a migration and costs nothing.
The day there are rows, it is still a rename — just one that needs a maintenance window.

## Decision 4 — `Kind` is stored as text

`Company` / `Candidate`, `nvarchar(16)`, not `int`. A waiting list is a table somebody opens in
a query window long before there is an admin screen, and `Kind = 1` in a result grid is a number
you have to go read the source to understand. The cost is a few bytes a row on a table that will
not see six figures.

## Decision 5 — The app does not migrate itself on startup

`Database.Migrate()` in `Program.cs` is one line and it is wrong here twice over. The Container
App can run several replicas: whichever boots first takes a schema lock while the others fail
their readiness probe. And it means the login the app runs as needs DDL rights **permanently**,
to do something that happens once per release.

Migrations are a deploy step. The commands are in [`docs/database.md`](../database.md).

## Decision 6 — The app refuses to start without a connection string

`ConnectionStrings:Leads` missing outside the tests throws at boot. The alternative is a
container that starts, passes liveness, and throws a 500 at the first person who types their
address into the form. A deploy that is wrong should be obvious while somebody is still
watching the deploy.

The opt-out is a setting, `Testing:AllowMissingDatabase`, not a check on the environment name,
because `UseSetting` is the channel `WebApplicationFactory` is guaranteed to reach. Setting it
in production does not get you a working API; it gets you a 500 on the first POST.

## Consequences

**Good**

- An address that is accepted is an address that is still there tomorrow. The landing page can
  finally be sent to somebody.
- The duplicate rule is enforced by the one thing that can see every replica at once.
- `/health/ready` now means something: it answers 503 while the database is unreachable, and
  Container Apps stops routing to that replica instead of restarting a perfectly healthy
  process.

**Bad, and worth saying out loud**

- **The migration is not covered by any test.** The integration tests run on SQLite and build
  their schema with `EnsureCreated()`, so they verify the *model*. Nothing in the suite checks
  that the *migration* still produces that model —
  `dotnet ef migrations has-pending-model-changes` is that check, and it belongs in CI.
- **Real concurrency is not covered by any test either.** Two SQLite connections to `:memory:`
  are two different databases, and a shared one serializes and starts answering "database is
  locked". What the tests do cover is the branch that runs when the index fires — deterministically,
  by making the second registration lose. The guarantee itself is the index, and the index is
  asserted by `EfCoreLeadStoreTests` and readable in the generated migration.
- Signing up now depends on the database being awake. On the serverless tier that means the
  first request after an idle period pays a few seconds. `EnableRetryOnFailure` is what keeps
  that from being a failed signup rather than a slow one.
